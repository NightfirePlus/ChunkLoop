# 真实模型验证记录（2026-10-30）

## 范围与配置

本次使用已有的阿里云百炼北京工作空间 OpenAI 兼容端点，未在仓库中保存端点凭证。模型列表接口返回 184 个可见模型；本次实际调用 `qwen3.8-flash` 做规划、`deepseek-v4.1-flash` 做写作、`glm-5.2` 做审核。规划和审核请求显式关闭思考模式，写作模型使用端点默认模式。请求使用 Chat Completions 的 `json_object` 格式；[阿里云接口文档](https://help.aliyun.com/zh/model-studio/qwen-api-via-openai-chat-completions/)说明此格式和 `enable_thinking` 参数的用法。

本次验证拆成两部分：固定计划的**调度对照**用于判断真实 HTTP 调用是否重叠；自动规划的**完整链路**用于观察内容审核与成稿质量。两者不能混为同一个通过率。所有最终列出的运行均未设置单次调用超时。早期曾设 120 秒上限，导致一次审核调用超时；该结果只用于定位配置问题，不作为架构性能结论。

**设计更正（同日）：**早期代码沿用原软文项目的强制审核门禁，把模型返回的任何问题都映射为 `blocked`。这并非 ChunkLoop 使用者提出的通用约束，现已改为默认返回 `needs_review` 和草稿；只有调用方显式选用严格审核才会因未解决的模型意见阻断。本页早期运行数据保留为历史观察，不代表当前默认语义。下述“约 300–450 字”和“只用给定证据”来自本次自拟的验证样例，也不是 ChunkLoop 的默认限制。

## 1. 固定计划：串行与双队列对照

输入为 [`examples/live-architecture.json`](../examples/live-architecture.json) 的 4 个独立内容块。两组使用相同的模型、证据、块指令和单个写作／审核工作者，各运行一次；不执行整份终审，以隔离调度行为。

| 指标 | ChunkLoop 双队列 | 逐块串行基线 |
|---|---:|---:|
| 结果 | 4 块均通过 | 4 块均通过 |
| 墙钟耗时 | 5.886 s | 9.278 s |
| 写作／审核请求 | 4 / 4 | 4 / 4 |
| HTTP 写作耗时合计 | 4.585 s | 5.895 s |
| HTTP 审核耗时合计 | 3.643 s | 3.380 s |
| 写作与审核 HTTP 请求重叠 | **2.349 s** | 0 s |
| 首块通过（从双队列开始） | 1.859 s | 未单独记录 |
| 写作输出 token | 367 | 598 |

双队列墙钟时间比本次串行样本短 3.392 秒，降幅 36.56%。**可直接确认的架构事实是 2.349 秒真实请求重叠**。两次生成的文字和 token 数不同，外部模型服务延迟也会波动；单次对照不足以推断稳定加速比例或内容质量提升。以下命令复现方法；样例事实后来随默认审核策略更正，重新运行不会复得同一组数值：

```powershell
& '.\.conda\envs\ChunkLoop\python.exe' -m tools.compare_live --report .tmp\live-architecture-compare.json
```

## 2. 自动规划、分块审核与整份终审：更正前

当时的验证样例要求写约 300–450 字的技术介绍。无默认超时运行中，规划模型生成 4 块；4 块均一次通过逐块审核，随后整份终审返回 4 项问题，旧版强制门禁把状态标为 `blocked`。结果如下：

| 指标 | 结果 |
|---|---:|
| 分块队列加终审耗时 | 27.594 s |
| 从规划到错误主张探针结束的总耗时 | 33.753 s |
| 规划／写作／审核请求 | 1 / 4 / 6（审核含终审与探针） |
| 规划输入／输出 token | 440 / 382 |
| 写作输入／输出 token | 1516 / 2829 |
| 审核输入／输出 token | 2404 / 487 |
| 逐块审核通过数 | 4 / 4 |
| 整份终审 | 阻断，4 项问题 |
| 稿件长度 | 705 字符，超过任务目标 |

终审指出了“开发者依据 Issue 修改并再次提交”这类证据没有描述的流程。另几项把“哈希核对用于确认输入一致”“整份终审器检查整份结果”等较直接的释义判为无依据，说明审核口径也有过严的情况。更关键的是，**逐块审核没有发现跨块重复或整体篇幅超标，整份终审也没有指出篇幅问题**。这些是当前内容质量链路的待改进点；本次完整链路不能标为成功成稿。

同一审核模型还检查了故意错误的主张“系统自动验证全部证据来源真实性，审核绝不会漏检”，返回 `unsupported_claim`，说明这一个预设错误样本被检出。它不能证明一般性的漏检率。

当前代码可用以下命令重跑同类实验（从本地 `.env` 读取已有凭证，报告写到 Git 忽略目录）；审核状态会按更正后的默认策略解释，不能复得旧版 `blocked` 语义：

```powershell
& '.\.conda\envs\ChunkLoop\python.exe' -m tools.validate_live --planner qwen3.8-flash --writer deepseek-v4.1-flash --reviewer glm-5.2 --report .tmp\live-multi-model-no-timeout.json
```

## 3. 迭代与限制

| 运行 | 主要差别 | 结果 |
|---|---|---|
| 初次完整运行 | 默认思考模式；规划 9 块；人为设置单次 120 s 上限 | 审核调用超时并阻断。该上限已从默认配置移除 |
| 调整后完整运行 | 规划上限 6 块，规划和审核关闭思考模式；实际规划 4 块 | 逐块通过，整份终审因重复和无依据表述阻断 |
| 无默认超时完整运行 | 进一步约束块内证据与重复；实际规划 4 块 | 逐块通过，整份终审仍阻断；篇幅超标未被检出 |
| 固定计划调度对照 | 不运行整份终审，使用 4 个独立块 | 串行与双队列均通过；记录到 2.349 s 真实请求重叠 |

## 4. 更正后的默认审核复测

更新样例事实以反映当前“默认建议式、严格模式可选”的规则后，再次调用相同三类真实模型且不设置调用超时。4 个块均通过逐块审核；整份终审提出 5 项意见，系统返回 **`needs_review`、完整草稿和意见**，没有把模型意见当作执行故障。耗时为分块队列加终审 27.797 秒、从规划到错误主张探针结束 33.235 秒；规划、写作、审核分别调用 1、4、6 次，没有接口失败。

本次草稿为 697 字符，高于样例要求的约 300–450 字，终审未指出篇幅问题。5 项意见中有“队列分离可使写审并行”等可能过严的判断，应由人工核查，不能直接作为发布禁令。故本次证明了**结果与审核意见可分离返回**，不证明内容已经满足样例全部要求。更正后样例见 [`examples/live-technical-brief.json`](../examples/live-technical-brief.json)。

## 5. 无额外硬限制的创作样例

为了检查通用模块是否暗中要求字数或事实白名单，新增 [`examples/live-freeform.json`](../examples/live-freeform.json)：只要求用中文写一段有画面感的海上灯塔短篇随笔，`evidence` 为空，未给出数字篇幅或发布门禁。规划模型生成 4 块；4 块逐块审核通过，整份终审没有返回问题，状态为 `completed`。分块队列加终审耗时 21.797 秒，从规划到结束共 24.808 秒；写作／审核调用为 4 / 5 次，没有接口失败。

成稿为 836 字符，虽然没有违反数字上限，但对“短篇”的把握偏长。`completed` 只表示当前模型没有提出未解决的审核意见，不能代替用户对篇幅和风格的判断。这次结果支持“无证据时通用适配器仍可生成并返回作品”，不证明模型总能正确理解模糊的篇幅要求。

当前可下的结论是：**双队列在真实模型调用中确实重叠执行；默认审核意见会随草稿返回，执行错误与严格审核门禁才导致 `blocked`**。还不能声称自动规划后的稿件稳定符合用户篇幅要求，或双队列在不同负载下总能提高相同比例的速度。下一步应建立多样本基准，并用人工标注集校准审核漏检与误报。篇幅之类只有在用户明确要求时，才应进入确定性检查。
